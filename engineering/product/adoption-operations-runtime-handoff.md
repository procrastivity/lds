# Deterministic adoption plumbing: runtime handoff

**Status:** Implemented and tested on disposable targets in local, unpushed BDS-250 work. No named real pilot has been selected or authorized.

The five `lds docs` leaves implement the bounded [adoption operations contract](adoption-operations-contract.md) against an **explicit existing target root**. The contract's “not implemented” status is its frozen design-time wording; its bytes remain pinned by the [acceptance matrix](adoption-operations-acceptance.md). The [accepted adoption behavior](adoption-contract.md) still governs four output paths and preservation. That matrix and the [BDS-249 handoff](adoption-stage-3-handoff.md) are specifications and fixture provenance; the executable evidence below is separate. This handoff is for BDS-251 to consume plumbing, not evidence of an LLM workflow or a real-project adoption.

## Interface for a later approved workflow

| Leaf | Supported result or effect |
| --- | --- |
| `lds docs inventory <root> --json` | Sorted `schemaVersion: 1` scoped Markdown file hashes, supported inline/reference links, and explicit skips. Reads root `README.md` and Markdown under `engineering/` and `docs/`; it does not inspect the rest of the source tree as documentation. |
| `lds docs validate <root> --json` | Checks the file component of supported relative local links; missing files appear in `findings` and exit 1. Unsupported checks appear in `skipped`, not as successes. |
| `lds docs render <root> --facts <facts.json> --json` | Validates the complete owner-approved fact assertion and renders only the four approved assets, with exact prospective content, content hashes, and resolver source/hash. Does not authenticate the approver or independently prove the facts. |
| `lds docs plan <root> --facts <facts.json> --json` | Read-only four-path `create`/`identical-untouched`/`different-collision`/`refusal` preview, affected existing bytes/hashes, necessary parents, report-only root README notice, findings/skips, veto and `planDigest`. A collision or refusal vetoes **all** creates (exit 3); link findings alone are non-veto diagnostics. |
| `lds docs apply <root> --facts <facts.json> --plan <reviewed.json> --confirm <reviewed-planDigest> --json` | Requires the exact reviewed plan JSON and a separately obtained human digest confirmation; rejects veto, declined/stale inputs, changed root/parent identities, and unsafe paths. Creates only missing approved files with no-follow/exclusive operations on Linux. Reports observed `created`, `identicalUntouched`, `unattempted`, `failed`, `preserved`, and `status`; a late failure can be partial and is **not** rolled back. |

All five are `plumbing` in `lds manifest --json`; they have declared JSON schemas and reuse the existing structured error envelope. Exit 0 means eligible/clean or successfully applied/current; 1 means a validation finding or invalid render input; 2 means usage; 3 means policy refusal/collision/declined or stale confirmation; 4 means unexpected I/O/internal failure. A diagnostic `validate`, vetoed `plan`, or partial `apply` can emit both a result on stdout and an error envelope on stderr. Consumers must inspect both rather than treating any JSON stdout as success. A vetoed `apply` refuses before revalidation and leaves `preserved: []`; this is not observed preservation evidence, although the disposable test separately confirms unchanged bytes. Save and display the **whole** plan before requesting a human confirmation; never automatically extract its digest as approval. The digest commits to every displayed plan field except itself, including findings, skips, report-only notices, and root/parent identities. Apply re-plans before writing; a changed preview needs a new review. No `--force` or update-in-place path exists.

## Supported boundaries and explicit skips

- Empty or partially populated documentation layers are valid. A mixed root README remains unchanged. Recognizable or ambiguous legacy LDS under `docs/` refuses rather than migrating; `docs/reference/` alone is not conclusive. Differing or edited generated-looking outputs are collisions, not owned update targets.
- Inventory recognizes a bounded subset of inline and reference-style Markdown links outside code. Validation checks relative local **file existence**, not fragments. External URLs are not fetched; recognized fragment-only, query-bearing and image links are marked as skipped. Escaping/absolute or symlinked targets are not followed and have skip/refusal diagnostics. HTML links and unrecognized Markdown syntax are outside the scanner's coverage and may not appear even as skips. It is not complete Markdown parsing, external-link checking, or content verification.
- Facts are supplied by a caller with explicit approval/provenance and a verified operation. Structural checks and context-safe rendering cannot authenticate the owner or validate real-project claims. Only four fixed assets resolve through user-XDG → installed-default → embedded; there is no repository-local override layer.
- Plan/apply refuse unsafe targets and do not follow symlinks. Linux applies exclusive creates after rechecking the reviewed root and existing parent identities at the write boundary. This is neither cross-file atomicity nor immunity to a rename in the interval after the final check. A partial result is evidence for manual review and a **new** preflight, not permission to retry blindly. Other platforms refuse creation where the Linux no-follow/exclusive invariant cannot be met; cross-build success is not apply support.

## Executed evidence and remaining gate

`nix develop --command go test -v ./internal/cli -run '^TestDocsAdoptionRuntime_PreservationMatrix$' -count=1` executes the built CLI on a disposable greenfield Wordcount target and all eight [preservation overlays](../../internal/asset/testdata/adoption/preservation/cases.json). It compares the exact approved plan path/class set, exit/refusal codes, independently authored output bytes/hashes, reported created/identical and preserved path/hash/size sets, and before/after target bytes and fixture hashes. It exercises the Wordcount operation and a fresh identical zero-write rerun; veto cases create nothing. Additional [adoption tests](../../internal/adoption/apply_test.go) cover stale facts/assets/diagnostics/target identities, unsafe paths, late collision and partial I/O. [CLI tests](../../internal/cli/e2e_test.go) cover resolver precedence, missing facts, link diagnostics, decline, and JSON/exit behavior. Fixture projections alone did not establish these observations.

In this local checkout, `nix develop --command make check` passed (ShellCheck, golangci-lint **0 issues**, all Go packages); `nix develop --command go vet ./...` passed. `nix build --no-link --print-out-paths .#default` produced a package whose `lds manifest --json` lists all five `docs` leaves as plumbing and all four adoption assets with their checksums; the installed share tree contains those four assets. Static `darwin/arm64`, `linux/amd64`, and `windows/amd64` cross-builds passed; only Linux apply execution was exercised. These are local checks, not CI or published-release results.

**BDS-251 boundary:** It may orchestrate these deterministic leaves after obtaining target-specific owner-approved facts and a human-reviewed plan digest, but must not infer a real pilot, authenticate approval from fixture metadata, claim full link validation, migrate existing LDS trees, or add a porcelain/LLM workflow by implication. The accepted **1B** gate still requires separately naming and authorizing a real target before any real-target write. No other repository was used as an apply target here.
