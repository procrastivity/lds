# Deterministic LDS adoption operations

**Status:** Accepted design contract; not implemented

This specifies the deterministic operation boundary for [BDS-250](https://linear.app/beausimensen/issue/BDS-250/deliver-deterministic-lds-documentation-adoption-operations). The [adoption contract](adoption-contract.md) remains authoritative for facts, four outputs, preservation, and refusals; [ADR-0001](../decisions/0001-adopt-two-track-documentation.md) governs the two tracks and optional layers. The [BDS-249 handoff](adoption-stage-3-handoff.md) distinguishes fixture expectations from runtime evidence. The [roadmap](roadmap.md) proposes other workflows but does not specify or implement them.

The five planned leaves are `lds docs inventory`, `lds docs validate`, `lds docs render`, `lds docs plan`, and `lds docs apply`. Each is deterministic **plumbing**, registered through the existing CLI/manifest surface; none is an LLM workflow, an `init`/`assess` porcelain verb, or a claim that an adoption CLI currently exists. They operate on an explicit target root. `render`, `plan`, and `apply` consume a target-specific JSON fact file. `apply` additionally consumes a previously reviewed plan and an explicit approval of its digest. The CLI's existing global `--json` and `--verbose` flags remain global; no new distribution mechanism is needed.

## Target and read-only scope

The target root is an existing directory named explicitly for each operation, not an implicit current working directory. Paths in results are slash-separated and relative to that root; no operation may traverse outside it or follow symlinks. Inventory enumerates regular Markdown files at the root `README.md` and below `engineering/` and `docs/`, including partially populated trees. It lists their relative paths and byte hashes, and extracts local inline and reference-style Markdown links from those files. It does not enumerate the rest of the source tree as documentation. A symlink encountered in scope is reported as skipped rather than traversed.

Validation checks the file component of supported relative local links against the target tree. For example, `engineering/README.md` linking to `product/overview.md#current-capability` checks the existence of `engineering/product/overview.md`, **not** the fragment. A missing local file is a finding; an absent optional LDS layer or an entirely fresh documentation tree is not. An absolute or escaping local path is not followed and is reported as unsupported/unsafe. External URLs are never fetched. Fragment-only links and fragment existence, query-bearing links, images as images, HTML links, and Markdown syntax outside the supported inline/reference forms are not validated; recognized skips carry a reason. The result must not imply complete Markdown or external-link coverage. Legacy-LDS signals under `docs/` can be reported read-only; their adoption refusal is decided by preflight, not by relocating them.

## Facts and rendering

The JSON fact file supplies the owner-approved display name and one-sentence purpose, a current capability with source citation, and a verified user operation with prerequisites, exact invocation/input, observed or source-backed output, limitations, and evidence source. It also records who approved the facts and their provenance. The field set corresponds to the four [shipped templates](adoption-template-assets.md): `DisplayName`, `Purpose`, `CurrentCapability`, `DisplayNameSource`, `PurposeSource`, `CurrentCapabilitySource`, `Prerequisites`, `OperationName`, `OperationSummary`, `Invocation`, `Input`, `OutputEvidence`, `OperationSource`, and `Limitations`, plus approval metadata. Require nonempty values and explicit approval/evidence for all four fact groups before an adoption plan is eligible. No default project identity, inferred future behavior, or placeholder prose is allowed. Structural validation can require citations and an approval assertion; it cannot authenticate an approver or independently prove a project's claims. Fixture-owner approval is test-only and never authorizes a real repository.

`render` resolves only these four relative asset names through the existing user-XDG → installed → embedded chain, preserving the resolver's shadow-by-name behavior:

| Asset under `assets/templates/adoption/` | Target output |
| --- | --- |
| `engineering/README.md` | `engineering/README.md` |
| `engineering/product/overview.md` | `engineering/product/overview.md` |
| `docs/README.md` | `docs/README.md` |
| `docs/reference/usage.md` | `docs/reference/usage.md` |

The renderer accepts only the declared fact fields and fails on missing or invalid template actions/fields, including in an override. Fact strings are plain text, not trusted Markdown or template source. Render each value for its Markdown context so it cannot introduce a heading, link, HTML, code delimiter, or new template action. Preserve intentional text and line breaks without allowing a new Markdown block; reject unsafe controls and unsafe local source references. Render deterministic UTF-8 with LF line endings. The present `docs/reference/usage.md` asset wraps `{{.Invocation}}` in single backticks, which is unsafe when an invocation contains backticks or newlines. Implementation must adjust that template/context to use a code delimiter or fence longer than any delimiter run in the value, then update independent expectations for any changed bytes. Raw substitution into the current backticks is not an accepted shortcut. Test Markdown metacharacters, brackets/links, backticks, multiline values, and malformed overrides as well as ordinary fixture facts.

`render` is read-only and reports the exact prospective content, SHA-256, and resolved asset source/byte hash for each of the four paths. Its content must be the content `plan` compares and `apply` would create for the same facts/assets. No repository-local override layer is implied.

## Result and exit contract

Under `--json`, each successful or diagnostically complete leaf emits **one JSON object on stdout** with `schemaVersion: 1`, `operation`, and operation-specific fields. Arrays are present as `[]`, not `null`; paths use relative slash form and arrays are sorted by path, then source location, then stable code. Do not put timestamps or unordered map iteration in results. The target-root identity is a separate field where needed for plan/apply; paths within findings and outputs remain relative. New leaves declare their actual output schemas in the manifest, without changing the manifest schema version solely for new verbs.

| Operation | Required result fields beyond `schemaVersion`, `operation` |
| --- | --- |
| `docs inventory` | `files` (`path`, `sha256`, `size`), `links` (`source`, `line`, `target`, `kind`), `skipped` (`source`, optional `line`, `code`, `reason`). |
| `docs validate` | `findings` (`code`, `path`, optional `line`/`target`, `message`), `skipped` (`source`, optional `line`, `code`, `reason`). A broken local target has a stable finding code; an unchecked external URL has a skip code, not a passing check. |
| `docs render` | `outputs` (`path`, `content`, `sha256`, `asset` with relative name, resolver source, and byte hash). |
| `docs plan` | `targetRoot`, `planDigest`, `factsDigest`, `outputs` (`path`, `classification`, `reason`, and, when renderable, the render fields and optional `existingSha256`), `necessaryParentDirectories`, `preserved`, `reportOnly`, `veto`, `findings`, `skipped`. Include prospective content so eligible bytes are reviewable. A refused incomplete-facts plan has `planDigest: null` and cannot be applied. |
| `docs apply` | `planDigest`, `status` (`applied`, `current`, `refused`, or `partial`), `created`, `identicalUntouched`, `unattempted`, `failed`, and `preserved`. Each path record includes its relative `path` and observed byte hash if readable; a failure record also includes a stable code and message. Report actual effects, not only planned actions, including on late failure. |

Classification values are exactly `create`, `identical-untouched`, `different-collision`, and `refusal`. A plan with one different output may still classify the other three as `create`, but has `veto: true` and creates **none**. A missing required user-operation fact refuses the entire attempt, not just `docs/`. An identical four-output tree has four `identical-untouched` classifications, `veto: false`, and no prospective writes. Necessary parent directories include only missing parents of approved outputs. `reportOnly` includes a root README signpost notice when applicable; it never proposes a README edit.

Reuse the CLI's existing structured error renderer and exit table. Exit 0 means a clean read-only result, an eligible plan, or successful/no-op apply. Exit 1 means read-only validation findings or invalid render input; 2 is Cobra usage/flag failure; 3 is a policy refusal, collision, declined/stale approval, or unsafe target; 4 is unexpected internal/I/O failure. A diagnostic `validate` or vetoed `plan` still writes its result object to stdout before returning 1 or 3 respectively; the existing structured `{"error":{"code","message"}}` envelope appears on stderr in `--json` mode. A usage failure follows Cobra's existing usage path, not a fabricated success object. An I/O failure that prevents a complete read-only result need not emit an incomplete success object. On partial apply failure, however, emit an actual-effects result as far as it can be determined and the error envelope/exit 3 or 4. Stable diagnostic codes distinguish, for example, a broken local target (`validation.local-target-missing`, exit 1) from an occupied different output (`refusal.output-collision`, exit 3); messages are for humans, not parsing.

For example, with three missing outputs and an occupied, differing `docs/reference/usage.md`, a plan result has `outputs` classifications of three `create` and one `different-collision`, `veto: true`, and a digest identifying that refused preview; the digest cannot authorize application. It exits 3, with the result on stdout and a `refusal.output-collision` envelope on stderr. In contrast, a read-only broken relative link appears in `validate.findings` and exits 1; an unchecked `https:` URL appears in `validate.skipped` and does not by itself fail validation. A plan that only reports that broken link and external-link skip remains eligible and exits 0. These are separate streams and outcomes, not two JSON objects concatenated on stdout.

## Reviewed plan and application

`plan` first validates the complete fact bundle, renders all four assets, inventories relevant target state, and presents a preflight before any writes. It runs the bounded local-link check over scoped existing Markdown and the four prospective outputs as a virtual overlay, placing broken-file diagnostics in `findings` and unchecked links in `skipped` for review. Broken links and skips **alone do not veto creation or change plan exit 0**; only an independently named policy refusal (such as unsafe path or legacy layout), incomplete facts, or a different-byte collision vetoes. A diagnostic that also proves a named refusal is classified and reported as that refusal, not promoted merely because it is a link finding. The plan identifies every approved path as `create`, `identical-untouched`, `different-collision`, or `refusal`; lists affected existing/preserved paths, reasons, and the report-only root README signpost opportunity; and vetoes **all** creates on any collision or refusal. Recognizable or ambiguous legacy LDS under `docs/` (including a partial tree explicitly rooted there), unsafe symlink output/ancestor, or unreadable occupied path refuses. `docs/reference/` alone is not conclusive evidence of legacy LDS. An unambiguous partial `engineering/` tree may receive missing approved files. No migration, replacement, deletion, move, other output file, or unused directory is authorized.

The plan digest is `sha256:<hex>` over the RFC 8785 canonical JSON encoding of the **entire displayed plan object except `planDigest` itself**. Every review field is included, without exclusions: root identity, `factsDigest` (committing to the complete facts and approval/provenance), asset source and byte hashes, rendered output content and hashes, candidate/parent and preserved-path evidence, `veto`, `findings`, `skipped`, `reportOnly` notices, and any future displayed fields. Arrays follow the result's specified stable sort order before canonical encoding. A change to a broken-link diagnostic, skipped check, or README notice therefore changes the reviewed digest even when candidate output bytes do not. A plan is not a durable ownership stamp and does not grant permission to update generated-looking files. Its JSON is the review artifact; `apply` consumes that exact plan and an explicit confirmation of its digest, but refuses any plan with `veto: true` even if its digest is confirmed. There is no `--force` or implicit approval. The CLI can check the supplied digest, not prove that a human supplied it; the caller must obtain human confirmation of the displayed plan.

Before writing, `apply` revalidates the facts, assets, root, candidates, parents, relevant preservation/legacy evidence, bounded link diagnostics, and report-only notices and recomputes the digest. Any change to the reviewed inputs or target state refuses as stale, with no creates. It must not silently replan and apply a different result. Declining confirmation also writes nothing. An identical rerun can be reviewed and confirmed as a no-op: all four outputs remain byte-identical and zero writes occur. Changed facts affecting an occupied output collide rather than update it.

After a successful recheck, creation must not follow a symlinked output or ancestor and must use exclusive creation so a newly occupied file is never truncated or replaced. If the platform cannot meet that no-follow/exclusive invariant, refuse rather than weaken it. A race or I/O failure during creation may leave a subset of **newly created** files or an incomplete new file; report the paths and actual observed state, mark unattempted paths, exit nonzero, and do not claim a transaction or roll back by deleting existing content. A new preflight/review is required before another attempt. This preserves the BDS-249 **all-create preflight veto**, which is not a crash-safe or cross-file atomicity guarantee.

## Runtime evidence and limits

Exercise the executable leaves on disposable copies of the BDS-249 greenfield and preservation fixtures, plus missing-fact, broken-local-link, unsafe fact/template, stale-plan, symlink, and target-change cases. Compare rendered bytes against independent expected content; snapshot target files before each attempted apply and compare bytes and hashes afterward. In particular, prove fresh four-file creation, valid absent layers and partial engineering content, mixed root README preservation, collision/edited-output veto of all creates, legacy/ambiguous `docs/` refusal, declined/stale approval with no writes, and an identical second application with zero writes. Test the user-XDG, installed-default, and embedded paths through the runtime renderer. Record exact commands, JSON, exit codes, and skipped checks. The existing asset fixture tests alone do not establish any of these runtime claims.

The accepted **1B** boundary still defers a named real pilot: no real repository has been selected or authorized for modification. A passing disposable runtime suite establishes the bounded operation contract, not real-project usability, content accuracy, full Markdown validation, or migration. BDS-251 may consume these plumbing operations in a later workflow; it does not change their scope here.
